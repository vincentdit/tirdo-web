# Internationalization (EN / SW)

The site is bilingual: **English (default)** and **Kiswahili**, built on
[`next-intl`](https://next-intl-docs.vercel.app/) v3.

## How it works (Phase 1 — cookie-based, no URL prefix)

- Locale is stored in the **`NEXT_LOCALE` cookie**. There is no `/en` or `/sw`
  URL segment yet, so existing links and routes are unchanged.
- `src/i18n/config.ts` — the locale list (`en`, `sw`), default, and display names.
- `src/i18n/request.ts` — reads the cookie per request and loads the matching
  catalogue; falls back to English when the cookie is missing/invalid.
- `src/i18n/locale.ts` — a server action (`setLocale`) the switcher calls.
- `next.config.js` — wraps the config with the `next-intl` plugin.
- `src/app/layout.tsx` — sets `<html lang>` and wraps the tree in
  `NextIntlClientProvider`.
- `src/components/site/language-switcher.tsx` — the EN⇄SW toggle in the header
  utility bar. It persists the choice, then refreshes so server components
  re-render in the new language.

## Message catalogues

Translations live in `messages/en.json` and `messages/sw.json` with identical
key trees. Components read them with `useTranslations()` (client and server)
or `getTranslations()` (async server components).

Navigation labels are keyed: `src/lib/site.ts` carries a `key` on every nav
node (namespace-relative under `nav`), and the header, footer and sitemap
render the translated label via that key. The English `title` on each node is
kept as the source/fallback text.

### Adding or changing a label

1. Add the key to **both** `messages/en.json` and `messages/sw.json`.
2. Reference it with `t("your.key")`.

Keep the two files in structural sync — a key present in one and missing in the
other will fall back to the key name at runtime.

## Scope

**Translated now:** the whole UI chrome — top navigation and mega-menus,
header masthead, footer, visitor widget, sitemap, and common labels.

**Not yet translated:** long-form page *body* content (about, services,
department and news pages). These remain English and should be translated
incrementally — ideally as bilingual fields in the CMS so editors can maintain
Kiswahili without code changes.

## Phase 2 — locale-prefixed routing (`/en`, `/sw`)

When translated page content is ready, promote to prefixed routes for proper
per-language SEO and shareable URLs:

1. Move `src/app/*` routes under `src/app/[locale]/`.
2. Add `src/middleware.ts` using `next-intl/middleware` for locale detection
   and redirects, and switch `request.ts` to derive the locale from the route
   segment.
3. Replace `next/link`/`useRouter` with the locale-aware navigation helpers
   from `next-intl/navigation`.

Because all labels are already keyed, Phase 2 is a routing change — **no
re-translation** of the catalogues is required.
